# Air-Raid Alert Gateway (шлюз повітряних тривог) на базі MeshCore

> **Це форк [MeshCore](https://github.com/meshcore-dev/MeshCore)** — універсальної бібліотеки
> для multi-hop LoRa-маршрутизації. Ліцензія MIT зберігається (див. [license.txt](license.txt)).
> Цей README описує **надбудову**, додану в цьому форку: шлюз повітряних тривог поверх
> стандартного `companion_radio`. Оригінальний README проєкту MeshCore — у
> [README-meshcore.md](README-meshcore.md).

Шлюз повітряних тривог на базі MeshCore для Кривого Рогу.

## Що це

Firmware для `companion_radio` (роль Companion, не repeater/room-server), що перетворює стан
повітряної тривоги з інтернету на повідомлення в LoRa-мережі MeshCore — доступне навіть тим,
у кого немає власного інтернету, але є mesh-покриття.

## Що робить

- Опитує bulk-ендпоінт [alerts.in.ua](https://alerts.in.ua) по WiFi кожні 15 секунд:
  ```
  https://api.alerts.in.ua/v1/iot/active_air_raid_alerts.json
  ```
  Зверніть увагу: **без `<uid>` у шляху** — це один загальний ендпоінт для всіх локацій, на
  відміну від застарілого `.../active_air_raid_alerts/<uid>.json`.
- Відповідь — один JSON-рядок, символ на кожну локацію, наприклад `"NNNPN...A...N"`, де кожен
  символ — стан однієї локації (`N` = немає тривоги, `A`/`P` = тривога). `ALERTS_UID` у конфігу —
  це **0-based індекс символу** в цьому рядку (не частина URL). Прошивка бере
  `body[ALERTS_UID]` (з поправкою на лапки навколо JSON-рядка) і читає стан лише своєї локації.
- При **зміні** стану (тривога ⇄ відбій) шле повідомлення у ваш власний груповий LoRa-канал
  MeshCore (див. розділ [Канал](#канал) нижче) — його отримують усі учасники mesh-мережі в
  радіусі покриття, незалежно від того, чи є в них інтернет.
- Перше зчитування після старту — беззвучне (встановлює базовий стан, не шле повідомлення).
- Під час тривоги додає до повідомлення рівень і тип загрози (дрони, ракети тощо) — див.
  [Деталізація загроз](#деталізація-загроз).

## Деталізація загроз

Повідомлення про початок тривоги містить рівень небезпеки і перелік загроз:

```
🔴 ТРИВОГА — Кривий Ріг 22:22 (дрони, ракети)
🟡 ТРИВОГА — Кривий Ріг 22:22 (дрони)
🟢 Відбій — Кривий Ріг 22:47
```

🔴 — червоний рівень, 🟡 — жовтий (поле `alert_level` у даних alerts.in.ua). Типи загроз
перекладаються українською: `дрони`, `ракети`, `балістика`, `крилаті` тощо. Якщо рівень відомий,
а загроз не перелічено, дужок просто немає.

**Звідки дані.** Сам стан тривоги, як і раніше, визначає bulk-опитування (див. вище). У момент
переходу **відбій → тривога** шлюз робить додатковий запит до
```
https://api.alerts.in.ua/v1/alerts/active.json
```
і шукає там запис повітряної тривоги (`alert_type: air_raid`). alerts.in.ua веде такий
запис окремо для трьох рівнів: район (`location_uid` **46**), громада (**279**) і саме
місто (**5279**) — підвищення до червоного alerts.in.ua може поставити на будь-який із
трьох, тож шлюз збирає всі три й бере максимальний рівень і об'єднаний перелік загроз.
Лише якщо жодного з трьох немає — бере запис **9** (Дніпропетровська область).

**Зміна рівня під час тривоги.** Перший рівень може бути занижений — alerts.in.ua іноді дописує
червоний із запізненням. Тому, поки триває тривога, шлюз перечитує ці дані: через ~30 с після
початку і далі раз на хвилину (разом з основним опитуванням це 5 запитів/хв при ліміті 12).
В канал іде реальний рівень, в обидва боки:

- **Підвищення — одразу.** Якщо рівень зріс до 🔴 або з'явився новий тип загрози:
  ```
  🔴 ПІДВИЩЕНО — Кривий Ріг 22:23 (дрони, ракети)
  ```
- **Пониження — лише після двох районних перечитувань поспіль** із нижчим рівнем (щоб не
  заспокоїти людей через дані, спіймані посеред оновлення). Читання без запису району між ними
  (лише обласний запис) обриває серію, і відлік починається заново:
  ```
  🟡 ЗНИЖЕНО — Кривий Ріг 22:41 (дрони). Тривога триває.
  ```
  «Тривога триває» — обов'язково: 🟡 це не відбій. Якщо після цього рівень знову зросте до 🔴,
  повторне «ПІДВИЩЕНО» піде знову.

Повторів немає. Зникнення загрози без зміни рівня не оголошується. Відбій скидає стан.
Якщо перше повідомлення пішло без рівня (детальний запит не вдався), воно несло 🔴. Тоді
перечитування з 🔴 дає «ПІДВИЩЕНО» одразу, а з 🟡 — «ЗНИЖЕНО» після тих самих двох підтверджень.
«ЗНИЖЕНО» надсилається **лише за даними району/громади/міста** (uid 46/279/5279): запасний
обласний запис (uid 9) може тільки підвищувати рівень. Якщо є лише обласний жовтий, канал
мовчить, а OLED показує `TRYVOGA Y`.
OLED завжди показує поточний рівень з останнього перечитування, тож `TRYVOGA R` стає
`TRYVOGA Y` одразу, ще до того, як пониження підтвердиться для каналу.

> ⚠️ **Перелік загроз — об'єднання з усіх знайдених записів** (район + громада + місто), а не
> лише з одного. Якщо жоден із трьох не знайшовся, береться запис області (fallback) — тоді
> загроза ширша за місто: «ракети» означає загрозу для області в цілому, а не обов'язково саме
> для Кривого Рогу. Сам факт тривоги й відбою — як і раніше, для вашої локації `ALERTS_UID`.

**Безпечна деградація.** Якщо детальний запит не вдався (таймаут, помилка HTTP, rate limit,
незрозуміла відповідь, немає запису чи рівня), іде звичайне повідомлення без деталей:
```
🔴 ПОВІТРЯНА ТРИВОГА — Кривий Ріг 22:22
```
Тривога **ніколи не губиться** через деталізацію: вона лише доповнює повідомлення, коли дані є.
Помилки детального запиту не впливають на 15-секундне опитування стану.

### Як налаштувати під своє місто

Uid деталізації задаються в `AirRaidGatewayConfig.h` (необов'язково, без них — 46/279/5279/9):

```cpp
#define ALERT_DETAIL_LOCATION_UID "46"    // uid вашого району в /v1/alerts/active.json
#define ALERT_DETAIL_HROMADA_UID  "279"   // uid вашої громади
#define ALERT_DETAIL_CITY_UID     "5279"  // uid вашого міста
#define ALERT_DETAIL_FALLBACK_UID "9"     // uid вашої області (fallback, якщо жодного з трьох немає)
```

Значення пишуться **в лапках** — прошивка порівнює `location_uid` як рядок.

Це **не те саме**, що `ALERTS_UID`: `ALERTS_UID` — позиція символу в bulk-рядку (для Кривого Рогу
`279`), а тут потрібен `location_uid` району/громади/міста й області з `active.json` (для
Криворізького району, громади й міста — `46`/`279`/`5279`; збіг цифр `279` з `ALERTS_UID` —
випадковість, це різні простори значень). Де взяти:

- у «Повному списку локацій» alerts.in.ua (Google-таблиця, посилання на
  [devs.alerts.in.ua](https://devs.alerts.in.ua)) — знайдіть свій район, громаду, місто й область;
- або прямо в `active.json` під час тривоги у вашій локації: знайдіть запис із назвою свого
  району/громади/міста й візьміть його поле `location_uid`.

## UID — як знайти для свого міста

`ALERTS_UID` — це індекс вашої локації в bulk-відповіді, і він **не збігається** з офіційною
таблицею UID 3–31 з документації alerts.in.ua — та таблиця охоплює лише **області** (region-level,
окремий, менший простір значень). Для міст/громад потрібен **повний список локацій** — Google-таблиця,
посилання на яку є на [devs.alerts.in.ua](https://devs.alerts.in.ua). Знайдіть свій населений пункт
у повному списку та візьміть його індекс.

Приклади (перевірено проти живих даних):
- `279` — м. Кривий Ріг + Криворізька громада
- `9` — Дніпропетровська обл. (рівень області, покриває Кривий Ріг як fallback, якщо
  city-рівень чомусь недоступний)

Сервіс документує лише коди помилок 401 (поганий/протермінований токен) і 429 (rate limit).
HTTP 404 сигналізує про **старий, вже не чинний** шлях `/{uid}.json` — з поточним bulk-ендпоінтом
його ви не побачите.

Обмеження запитів alerts.in.ua — 12 req/min; прошивка опитує раз на 15 с, з подвоєнням інтервалу
(до 5 хв) при HTTP 429.

## Канал

**Не використовуйте PSK з цього README чи з чужого форку.** Кожен розгортає свій шлюз зі
**своїм власним** каналом:

1. У застосунку MeshCore (телефон/десктоп) створіть новий груповий канал — назвіть його
   під своє місто (наприклад, `"Тривога <Місто>"`) і згенеруйте PSK там само.
2. Впишіть цю назву й PSK у **свій** `CHANNEL_NAME` / `CHANNEL_PSK_HEX`.

Чому це важливо, а не просто формальність:

- **Різні міста — різні канали.** Якщо всі форки цього проєкту використовуватимуть один і той
  же канал, тривоги різних міст змішаються в одному потоці, і отримувач не зможе зрозуміти,
  до якого міста повідомлення стосується.
- **Публічний PSK = відкриті двері для фальшивих тривог.** PSK — це весь захист каналу. Якщо
  його опублікувати (наприклад, у README), будь-хто зі стандартним клієнтом MeshCore зможе
  надіслати в канал фальшиву тривогу чи фальшивий відбій — а це вже питання безпеки людей, не
  просто спаму.

## Функції на пристрої

- **AIRRAID** — головна OLED-сторінка: напис **TRYVOGA** / **VIDBIY**,
  час останнього успішного опитування API, стан WiFi, напруга батареї, NTP-годинник.
- **DIAG** — діагностична сторінка (uptime, вільна пам'ять/стек у % і байтах, лічильник непрочитаних
  повідомлень) — зручно для довготривалого спостереження за стабільністю (soak-тест).
- Екран автоматично прокидається на будь-яке вхідне повідомлення (DM або канал) і при зміні стану
  тривоги, навіть якщо до того згас за таймаутом бездіяльності.
- Текст сторінок статусу/діагностики — латиницею навмисно: стандартний шрифт OLED-дисплея не має
  кириличних гліфів. Повідомлення в самому LoRa-каналі (яке бачать на телефоні/десктопі) лишається
  кирилицею.

## Gotchas / граблі

Речі, які на практиці ламали прошивку чи поведінку пристрою — якщо повторюєте збірку на своєму
залізі, врахуйте одразу:

- **Кнопку паяти на GPIO4, НЕ на GPIO12.** GPIO12 — strapping-пін (MTDI/VDD_SDIO flash voltage
  select). Зовнішнє підтягування на ньому під час reset ламає flash-strapping — плата валиться в
  `SPIFFS mount failed` і одразу хибно входить у CLI Rescue (сприймає плаваючий пін як затиснуту
  кнопку). GPIO0 — теж strapping (BOOT), теж не чіпайте.
- **Кнопка на GND потребує `INPUT_PULLUP` + debounce ~25мс.** Без цього дребезг контактів дає
  фантомні double/triple click — кнопка поводиться нестабільно навіть при одному фізичному
  натисканні.
- **Час — з NTP, не з mesh-годинника.** У mesh-мережі час синхронізується між вузлами, але без
  RTC-модуля з батарейкою це недостатньо точно для міток часу в повідомленнях тривоги — тому
  час береться окремо через NTP.
- **HTTP-опитування — в окремому FreeRTOS-таску, не в `loop()`.** Синхронний HTTP-запит
  (WiFi/TLS-хендшейк) блокував основний `loop()` на секунди — кнопка й UI підвисали під час
  кожного опитування. Опитування винесене в окрему задачу на іншому ядрі, а `loop()` лише читає
  готовий результат з черги.

## ⚠️ Застереження

Це **додатковий** канал попередження, а **не заміна** офіційних сирен, застосунку "Повітряна
тривога" чи інших офіційних джерел оповіщення. Дані надходять з неофіційного джерела
(alerts.in.ua), можливі затримки чи збої опитування (WiFi, rate limit, недоступність API). Сам
alerts.in.ua прямо зазначає: **не використовуйте для критичної інфраструктури**.
**Не покладайтеся на цей пристрій як на єдине джерело інформації про повітряну тривогу.**

## Альтернативна плата: ESP32-DEV + E22 (variant `esp32_loraprs_e22`)

Крім штатних плат MeshCore (Heltec, T-Beam тощо), у `variants/esp32_loraprs_e22/` є variant під
саморобну плату ESP32-DEV + окремий модуль E22 (SX1268), зібрану за схемою
[sh123/esp32_loraprs](https://github.com/sh123/esp32_loraprs) (`variants/esp32dev_e22`).

**Це звичайний MeshCore BT Companion, БЕЗ функціоналу повітряних тривог.** Середовище
`Esp32_loraprs_E22_companion_radio_ble` збирає стоковий `examples/companion_radio` без
`WITH_AIR_RAID_GATEWAY` — просто радіоміст по Bluetooth до застосунку MeshCore, без опитування
alerts.in.ua, без сторінок AIRRAID/DIAG тощо (їх і не може бути — на цій платі немає дисплея).
Щоб додати сюди air-raid функціонал, потрібно окремо прописати `-D WITH_AIR_RAID_GATEWAY` у
`platformio.ini` цього variant і завести свій `AirRaidGatewayConfig.h` (розділ Configuration
вище) — за замовчуванням це не увімкнено.

Збірка:
```
pio run -e Esp32_loraprs_E22_companion_radio_ble -t upload
```

**Радіопараметри за замовчуванням — ті самі, що й у шлюзу:** 433.650 МГц / BW 62.5 кГц / SF 8 /
CR 8. Свіжо прошита плата одразу працює в одній мережі зі шлюзом, нічого не треба налаштовувати
з телефона (BLE PIN — `123456`). Якщо на платі вже збережено налаштування від попередньої
прошивки, діють вони — тоді виправте їх у застосунку.

**Потужність передачі.** У прошивці `LORA_TX_POWER=22` — це значення для **чипа SX1268**, а не
потужність в ефірі. Модулі E22 з зовнішнім підсилювачем (PA), як-от **E22-400M30S**, на якому
перевірено цей variant, віддають в антену помітно більше, ніж виставлено на чипі (за даними
виробника — до 30 dBm / 1 Вт). Фактичний вихід залежить від модуля, живлення й антени, тож
виставляйте потужність з урахуванням цього й **у межах дозволеного** для діапазону 433 МГц у
вашій країні. За потреби зменште `LORA_TX_POWER` у `variants/esp32_loraprs_e22/platformio.ini`
(або потужність у застосунку). Живлення 1-ватного модуля має витримувати піки струму передачі.

Стан: **перевірено на залізі** (модуль E22-400M30S) — плата прошита, бачить репітери, канал
«Тривога KR» приходить на телефон по BLE.

**Піни** (NSS=5, RESET=27, DIO1=12, BUSY=14, RXEN=32, TXEN=33, MOSI=23, SCK=18, MISO=19) —
звірені з реальною KiCad-схемою проєкту esp32_loraprs (`extras/schematics/esp32dev/lora_tracker.sch`
+ netlist). П'ять пінів (RESET/DIO1/BUSY/RXEN/TXEN/MOSI) підключені жорстко — підтверджено
трасуванням доріжок. **NSS/SCK/MISO на цій платі йдуть через solder jumper'и JP1/JP2/JP3**
(це і є той самий вибір "36-pin vs 38-pin" плати з README esp32_loraprs) — значення 5/18/19 це
стандартний варіант ESP32 VSPI, на який розраховує і сама офіційна прошивка esp32_loraprs. Якщо
на вашому екземплярі плати запаяно інакше — радіо не проініціалізується при старті, і треба
звірити, яка сторона перемичок реально запаяна.

⚠️ Зверніть увагу: DIO1 сидить на **GPIO12** — це strapping-пін (той самий, що згаданий вище в
Gotchas для кнопки). У штатній роботі радіомодуля це не мало створювати проблем зі стартом (пін
конфігурується вже після завантаження), але якщо після прошивки цього variant плата не стартує
або сиплеться в `SPIFFS mount failed` / CLI Rescue — це перше, що варто перевірити.
